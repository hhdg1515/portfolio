Product Architecture Design Challenges

Two applications,
one clinical record system.

The public app was built for appointment requests. A separate, location-scoped staff console organized schedules, records, dental charts and treatment planning over the same shared dataset.

01 / 03

Architecture

No custom server. The entire security boundary lives in versioned database rules rather than application code.

The brief set that shape. The clinic asked for online booking and for staff to be able to look a patient up — which is not a website with a form on it, but two audiences over one dataset: a public side that takes appointments, and an internal side where records are reached. That needs identity, storage and a permission model from the first day rather than as a later phase. Firebase carries all three with nothing to run, which is how the security boundary ended up in rules instead of in server code.

Full stack breakdown
Shape
A monorepo holding two independent React 19 + TypeScript + Vite applications — public and intranet — driven by shared npm scripts with formatting enforced on commit.
Backend
Firebase supplies auth, database, storage and hosting. Security sits in versioned Firestore and Storage rules deployed by script.
Data
Nine collections covering appointments, confirmations, cancellations, patient profiles, dental charts and their snapshots, medical records and images, with hand-written composite indexes.
Clinical model
Per-tooth condition and severity across five surfaces; periodontal probing depths at three points on both sides plus bleeding points; treatment plans with priority and a status machine.
Operations
Scripts for bootstrapping the owner account, writing custom claims, seeding and resetting demo data with dry-run support, and deploying rules as part of the normal workflow.

Design

Reviewed by video, across a time zone

The walkthrough covered the way in from both sides: signing in from the public site with an administrator account, arriving at the dashboard, then reading the schedule and the current figures on the internal side. A time-zone gap made a live session impractical, so it went over as screen video to her phone — the running system, not a picture of one.

The next thing raised was a feature. The clinic runs a membership: enough spend across a year opens access to member events, and staff need to know which patient that applies to without going looking. So the member badge went into the admin view.

Requirements arrived that way throughout — in conversation, while the system was being walked through, rather than as a brief settled up front.

Teeth generated, not modelled

The 3D chart ships no model files. Four tooth archetypes are defined as parameter sets — crown height, root height, neck radius, squash ratios, cusp coordinates — and the geometry is generated at runtime, keeping the payload small and letting nine clinical states drive material colour directly.

Selected Detail

Two cache tiers with cross-tab invalidation

The database charges per read, so the console uses two cache tiers: an in-memory map with TTL and an IndexedDB layer that survives reloads and warms memory on startup. A broadcast channel tells other open tabs when to invalidate stale data. The cache is partitioned by business domain and degrades cleanly to memory-only.

It is also the one module with unit tests — not a coincidence, since it is the piece where being wrong costs money.

Permissions expressed declaratively

The rules file does multi-tenant access control without a line of server code: roles resolved from custom claims with a fallback, clinic-level isolation so an administrator only reaches their own locations, and field-level immutability preventing privilege escalation. Patients can cancel their own appointment but cannot move it. Everything ends in a default-deny catch-all.

Living with inherited data

A whole family of resolver functions exists purely to normalise legacy records whose fields had drifted — heuristics deciding whether a string looks like a date, a time, a phone number or a name. This is what integrating with a business that already had data looks like.

Challenges

01

Scope growth that outran the original stack

The intranet stayed on plain HTML and JavaScript while React was already running the public site in the same repository. It ended at 23,685 lines with no component model — and one hand-written build pipeline that told me it was time to stop.

Read the full write-up
Step 01Problem

The clinic initially wanted a simple front end, so the project started as plain HTML, CSS and JavaScript. Then the scope kept growing: multi-location permissions, an appointment state machine, the tooth chart, record uploads.

By the first commit the two halves were already on different stacks inside one tree: a React public site at 17,865 lines across 59 files, and a vanilla intranet at 11,918. They stayed that way for two and a half months. The tool that would fix the intranet was not something I had still to learn — it was running in the next folder.

The archived code shows where the intranet ended — 23,685 lines of hand-written source, with a single appointments file at 5,374 lines and no component model, so reuse happened by copying.

One honest caveat: the migration commit records the change but not the reasoning behind it. This problem statement is reconstructed from the archived code, not quoted from a discussion.

Step 02What I tried

First I tried to make it survivable in place — shared modules, a unified data access layer, and eventually a hand-rolled build pipeline: one script batch-minifying fourteen files, another rewriting every script tag to point at the minified output.

That pipeline is the tell. Hand-writing a build process means it is time to adopt a build tool. Six weeks later the migration landed — public site first, where the risk was lower; the console last.

Step 03The fix

One commit, 191 files changed, +35,000 / −37,005. It removed things too — drag-and-drop rescheduling was deleted outright, because the same operation already existed in the edit modal.

The line count did not collapse, and that is worth stating plainly: the intranet's 13,603 lines of hand-written JavaScript came out as 12,559 lines of TypeScript. What the migration bought was a component model, not less code.

What it kept is the part I would defend. The vanilla build already had a two-layer cache, and its header comment had already drawn the security boundary:

架构: - L1: 内存缓存 (Map) - 最快,页面内有效 - L2: IndexedDB - 持久化,页面刷新后仍有效 安全边界: ✅ 可缓存: 预约数据、统计数据、UI偏好 ❌ 不可缓存: 用户角色、权限、Token

That design was framework-independent, so it moved across intact and gained a third layer on the other side.

Step 04Outcome

191 files, a net reduction of roughly 2,000 lines, 23,685 lines of legacy JavaScript retired. Not measurable, and I will not claim otherwise — no before/after performance benchmark was captured. What can be stated is that reuse no longer required copying, and old URLs still redirect rather than 404.

  • Starting with vanilla was not the mistake. Not stopping at the third copy-paste was.
  • When you hand-write what a standard tool already does, your stack choice has expired.
  • Half the value of a migration is deciding what not to bring.
  • Architecture judgement is separable from framework knowledge.
02

A temporary permission loosening that scored itself

I widened the database rules to isolate a bug, and never put them back. A review a day later put a number on it: 92 to 42.

Read the full write-up
Step 01Problem

While debugging a stubborn permissions error, I widened the rules to rule out access control as the cause. The catch-all was the obvious one:

match /{document=**} { allow read, write: if isAuthenticated(); }

Any signed-in account could read or write anything. In a clinic system that means any patient login could reach every other patient’s records. The debugging worked. The rule never went back.

Step 02What I tried

The trail of candidate rule files shows the mistake. A permissive “temporary” version and a properly scoped version were written in the same commit. The correct approach was understood at the time; the permissive one simply got deployed to unblock the work.

That is what makes it a process failure rather than a knowledge gap:

Security Score: 42/100 (F) - Regression from 92/100 (A-)

The 92 had been earned by three phases of hardening the week before. One catch-all rule made all of it irrelevant, because every client-side check sits above the layer that was now open.

Step 03The fix

The catch-all was not reverted but rewritten: explicit per-collection grants ending in a default-deny. Role checks moved off the client into custom claims. The exposed key was rotated.

The process change mattered more — security rules went into version control and into a deploy script, so a rule change now travels the same review and rollback path as a code change instead of being pasted into a console.

Step 04Outcome

Regression closed; permissions went from one catch-all line to 215 lines of explicit authorisation. The post-fix score was never recorded — later audit documents exist but none states a figure — so the honest claim is “the regression was fixed”, not “restored to 92”.

  • A temporary permission change needs a scheduled reversal at the moment you make it.
  • Security is decided by the weakest layer, so the defence belongs closest to the data.
  • A review that produces a number moves people; “feels a bit loose” does not.
  • Treating security rules as code outlasts any single fix in that list.
